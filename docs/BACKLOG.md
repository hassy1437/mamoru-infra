## ※行の専用検査（不変条件①②③）— ★いまは作らない（2026-08-03 判断）

### なぜ「いま作らない」か
退行そのものは**ベースライン照合が捕まえる**。現実値セットに
`bekki11_1_test__autotest`（自動試験機能あり）のケースが載っており、
`autoTestSkip` / `isRowActive` を壊せば※行の矩形に差分が出て落ちる。
＝ **気づけない状態ではない**ので優先度は高くない。

### なぜ「いつか作る」か
落ちたときに**原因が「※行の話だ」と分かる名前の検査**があるほうが、
辿り着くのが速い。ベースライン照合は「どこかのページの何ピクセルかが変わった」
としか言わないので、※行の一括非表示が壊れたのか別の描画変更なのかを
その場で切り分けられない。

### ★作るときの不変条件（この3つ。件数で書かないこと）
1. **消えた行 = off で描かれていた※行**（集合として一致）
2. **※以外の行は1つも消えない**
3. **on に残った※行は0**

★**「23件消えること」を条件にしてはいけない。** ※行は定義上23件だが、
そのうち **3件（page2_rows の 5 / 9 / 11）は「なし」でも元から content を描いていない**
（`skipContentRows` に載っている＝テンプレートに選択肢が印刷済みで○を打つ行）。
実測値は **20 = 23 − 3**。件数を直接書くと**常に落ちる**。
だから条件①は「※行23件」ではなく「**off で描かれていた**※行の集合」と突き合わせる。

### 実測の根拠（2026-08-03）
一意マーカー（全65行に `P1_0`〜`P3_11`）を入れて off/on を生成し突き合わせた結果:
```
※行(定義) 23  内訳 {P1: 11, P2: 10, P3: 2}
うち off で実際に描かれていた: 20
on で消えた: 20 / 一致(消えた == off に出ていた※行): True
※以外で消えた行: 0 / on に残った※行: 0
off で描かれなかった※行: P2_5, P2_9, P2_11 ← 元から未描画
```

### 実装のとき
除外・判定は `src/lib/auto-test-rows.ts`（`isRowActive`）と
ルートの `autoTestSkip` と**同じ源から導出**すること。検査側に行番号を
書き写すとドリフトする。両方向の自己診断（`autoTestSkip` の戻りを
`undefined` に固定したら落ちる／現状で緑）と、`CHECKS` への登録
（`{ file, stage, why }`。STAGE 0 が孤立検査を検出するので登録必須）も要る。


## ★点検アプリ側にテストが1件も無い（2026-08-03 記録）

- PDF出力は `npm run check:pdf` の **52件**（静的・生成PDF・挙動・ベースライン照合）で守られている。
- ★**入力画面の状態管理は型検査以外に守るものが無い。**

### 今回それが実害になった

**往復（あり→なし→あり）で値が残ることを実測する手段が無かった**。
状態が `.tsx` の中（JSXを含む）に閉じていて単体で実行できず、
「labels を絞っていないから残るはず」で止まっていた。

### 暫定の対処（今回入れたもの）
- `src/lib/bekki-row-state.ts` … `hydrateRows` / `coerceRow` / `createEmptyRow` を
  コンポーネントから切り出し、単体で叩ける形にした。
- `scripts/check-bekki-row-state.ts` … 往復を実測する。ランナー無しで動く:
  ```sh
  node --experimental-strip-types scripts/check-bekki-row-state.ts
  ```
  ★`check:pdf` の登録簿には入れていない（PDFの検査ではないため）。
  入力画面の検査が増えるなら、そのとき束ねる口を作ること。

### 残っている判断
入力画面の状態管理が今後も増えるなら、最小の vitest を入れるほうが素直。
★今回は「ランナー導入」より「純関数として切り出す」ほうが影響が小さいと判断して見送った。


## 非該当欄の斜線 — ★入れないと決めた（2026-08-03）

### 決定
非該当の欄に斜線を引く機能は**実装しない**。既定オフのオプションとしても入れない。

★**「斜線が無い」を欠落と見て実装しに行かないこと。** 意図的に入れていない。

### 理由（決め手は非対称性）
- **求める人がいない**: 実務側（相棒）の確認で「引かなくても消防署から指摘は無い」。
  現時点で要求の実例が無い。
- **手書きで後から足せる**: 斜線は提出後の紙にペンで引ける。内容の改変ではなく
  「非該当」の明示なので訂正印の類も要らない。
- **誤って引いた斜線は消せない**: 斜線は空欄より強い主張になる（「点検していない」と読まれる）。
  非該当かどうかの判定を23様式ぶん抱えると、必ずどこかで誤判定が出る。
- ＝ **入れない場合の損失は「手書き1回」、入れる場合の損失は「消せない誤り」**。
  片方だけが回復可能なので入れない。

### ★条件つきで入れる場合
要求が実際に出たら、**その様式のその欄に限って**入れる。
全様式・全欄への一括適用はしない（上の誤判定リスクがそのまま戻るため）。

### 工数（そのとき用・実測ベース）
1. 斜線の描画ヘルパ新設 — 小。★現状 `pdf-form-helpers.ts` に線描画のヘルパは無い
   （`drawLine` / `drawSvgPath` とも0件）。`cellAt` の矩形の対角に1本引くだけ。
2. **「非該当」の判定定義 — ここが本体**。値が空なだけなのか点検対象外なのかを
   区別する必要があり、※印の一括非表示で入れた「自動試験機能あり」と同じ
   属性設計が要る。★これが決まっていないと着手できない。
3. 対象セルの宣言（適用する様式・欄のぶんだけ）
4. 既定オフの切り替えと、ベースラインPNG 62枚への影響確認


## PDF生成の呼び出し口を1つにする（`fetchPdf()`）

**状態**: 未着手（2026-07-25 記録）／優先度: 中（いま壊れてはいない。再発の予防）

### なぜ

⑧で各様式ルートが 422 に「どの項目が何文字超過か」を載せるようにしたのに、
呼び出し側が本文を捨てていて業者に届いていなかった。いまは共有ヘルパー
`src/lib/pdf-request-error.ts` を全経路に通し、`scripts/check-pdf-error-handling.py`
で「残り0件」を数えている。

ただし**この検査は対象を自分で探しにいく形**なので、新しい経路が増えたときに
すり抜ける余地が残る。実際そこで1度踏んでいる:

- 最初 `"/api/generate-"` のリテラルで対象を絞った
- → `apiPath` を prop で受ける `bekki-result-form-base.tsx`（16様式を担う最大の経路）が
  検査対象から外れたまま「OK」が出ていた
- ★共有化・パラメータ化されたコードほどリテラル検索から漏れ、しかも影響は大きい

恒久形は「PDFルートを叩ける口を1つにして、生の `fetch` を禁じる」こと。
そうすれば網羅は **「PDFルートへの生fetchが0件」** という単純な不変条件になり、
検査が対象を探しにいく必要がなくなる。

### 規模（実測 2026-07-25）

| | 箇所 |
|---|---|
| 生fetch地点 | **15**（コンポーネント14＋`build-merged-report` 1） |
| 用途: プレビュー（別タブ） | 9 |
| 用途: ダウンロード | 4 |
| 用途: 両方 | 1 |
| 用途: バイト取得（マージ） | 1 |

### 作業

1. `src/lib/pdf-client.ts` に `fetchPdf(url, payload): Promise<{ blob, warnings }>` を作る。
   失敗時は `PdfRequestError` を投げる（分類は既存ヘルパーを再利用）。約40行。
   ★別タブのプレビューは**ポップアップブロック対策でクリック同期に `window.open` してから**
   fetch している。ウィンドウの所有権は呼び出し側に残すこと（ヘルパーに持たせると壊れる）。
2. 15箇所を置換。各6行→4行程度だが、`URL.revokeObjectURL` や `previewWindow.close()` の
   後始末が絡むので機械変換ではなく1件ずつ確認する。
3. 検査を差し替え: `check-pdf-error-handling.py` の3規則を
   「`src/lib/pdf-client.ts` 以外にPDFルートへの生fetchが無い」1規則にする。
4. 陽性対照（両方向）を取り直す。

### 見積もり

**半日（3〜5時間）**。うち置換2時間・検査差し替え1時間・検証1〜2時間。

### リスク

プレビュー（別タブ）経路が9箇所と最多で、ここはポップアップブロックの都合で
ヘッドレス検証が難しい。**退行が出るとしてもここ**。実ブラウザでの
「様式を開く → PDF出力 → 別タブでプレビュー → ダウンロード」の手動確認が要る。

## 結合報告書のサイズを削る（23様式で77MB）

**状態**: 未着手（2026-07-25 記録）／優先度: 中〜高（下記の実害の順序を参照）

### 事実（実測）

| | サイズ |
|---|---|
| テンプレートPDF 1枚 | 0.18 MB |
| NotoSansJP-Regular.ttf | 5.20 MB |
| 生成された様式PDF 1本 | **3.25 MB** |
| 23様式を結合した報告書 | **76.95 MB**（62ページ） |

1様式に埋め込みフォントが158種（NotoSansJP のサブフォント群＋Helvetica）。
`subset:true` はCJKグリフが脱落するため採用不可と確定済みなので、
**埋め込み側では解けない**。23本それぞれがフォントを持ったまま結合され、重複排除もされない。

### ★実害は業者側の上流が先に来る

オーナーのダウンロードより、**業者が現場からモバイル回線で数十MBをアップロードする**方が先に詰まる。
納品ボタンは現場にいる業者が押す前提で、`deliver-report-button` は
生成した Blob をそのまま Storage に upload する。数十MBの上り＝時間・失敗率・通信量のすべてが効く。
＝ 優先度の根拠は「オーナーの体験」ではなく「納品が完了しないリスク」。

### 案(a) 結合後にフォントを統合する後処理

**支配的なコストは「Next.js のランタイムに載るか」。** PyMuPDF は使えない（Python）。
- qpdf / Ghostscript … ネイティブバイナリ。Cloudflare Pages / Vercel の実行環境に置けるか要検証。
  置けなければ別サービス（コンテナ）が要り、それ自体が新しい運用対象になる
- JS だけで完結する選択肢は要調査（pdf-lib にフォント統合の機能は無い）
- 見積もり: **調査1〜2日**（載るかどうかで結論が変わる）＋載る場合の実装0.5日。
  載らない場合はインフラ追加の判断が必要で、コストは跳ね上がる

### 案(b) 1パス生成にして埋め込みを1回にする

23ルートを「与えられた PDFDocument に描く関数」に変え、結合済みドキュメントへ順に描く。
フォント埋め込みが1回で済むので**後処理が不要**になり、理屈上 3.25MB×23 → 5MB台に落ちる。

- 改修量: 23ルート＋共有ヘルパー。各ルートは `PDFDocument.load` → `embedFont` →
  描画 → `save` の形なので、前後を剥がして「描画関数」を抜き出す
- 既存の単体PDF出力（様式ごとのボタン）は残す必要があるので、
  **薄いラッパで両対応**にする（描画関数＋従来のルート）
- 見積もり: **2〜3日**。ただし今日整えた検査がそのまま効く
  （ベースライン2系統・エラー経路・縮小警告・網羅性）ので、退行は検出できる

### どちらが安いか

**(b) の方が読める。** (a) は「載るか」が最大の不確実性で、載らなければコストが発散する。
(b) は改修量が大きいが見積もりが立ち、外部依存が増えない。
ただし (a) が載ると分かれば (a) が圧倒的に安いので、**まず (a) の可否を1〜2日で調べ、
ダメなら (b)** の順が合理的。
